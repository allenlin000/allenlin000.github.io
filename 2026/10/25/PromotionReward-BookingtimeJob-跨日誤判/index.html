Bookingtime Job 跨日誤判

Created2026-10-25|Updated2026-10-25|PromotionReward
|Post Views:

一筆訂單在午夜前成立，紀錄在午夜後更新。回饋時間稽核翻到它的 BookingTime，突然說：「這筆時間不對吧？」回饋紀錄大概只想回一句：「蛤？我不是照著排程來的嗎？」這場「各說各話」究竟是排程出了包，還是稽核拿錯時間對答案？先把兩邊看的時鐘攤開來看。

午夜前後，兩個時間點

BookingTime 像回饋單上的預約叫號時間。系統把它存進 DynamoDB 的 BookingTimeUTC；Dispatcher 到了查詢時段，依日期與時間找出待處理的回饋，接著安排給點或給券。稽核做的是另一件事：重新算一次「這筆原本該約幾點」，再和資料裡的時間對答案。一邊問「輪到這筆了嗎？」一邊問「這筆有沒有約錯時間？」同樣看時鐘，查的卻不是同一題。

同一個時間，兩種用途

這段先別讓時間線穿越。本文案例記錄於 2025 年 11 月；當時走到「加 N 天」分支的線上訂單，會以訂單成立時間為基準，先把時分秒歸零，再加上回饋天數。現行程式後來加入三桶分配，同樣先算目標日期，但會再排到 00:00、01:00 或 02:00。拿新版時刻表回頭對舊案，答案就容易越看越亂。

線上訂單先走哪條計算路徑？

「加 N 天」在案例當時與現在

時期 日期怎麼算 最後排到幾點
2025 年 11 月案例當時 OrderTime.Date.AddDays(N) 目標日期的 00:00
現行三桶分配 同樣先算目標日期，再交給 RewardBookingTimeAllocator 依穩定的訂單種子落在 00:00、01:00 或 02:00
這起跨日案例要先看當時的計算：+N 天 是以 OrderTime 的日期為起點，不是以稽核當下或紀錄更新時間重新起算。後面的稽核段落會檢查它拿哪個時間來對答案。

正流程排好時間後，稽核器就像拿著答案卡的監考老師。但它不能每張卷子都用同一份答案：已出貨、指定日期、券不足與尚未出貨，各有自己的計算規則。這起事件卡在「未出貨」的答案卡，重點是稽核究竟拿 OrderTime，還是 UpdateTime 當起點。

先選稽核路線

回饋類型 判斷順序 本文關注的入口
給點 略過指定狀態 → 已出貨且非指定日 → 指定日期 → 其餘 未出貨時進入 VerifyBookingTimeForUnshippedOrder
給券 略過指定狀態 → 近期券不足 → 已出貨 → 指定日期 → 其餘 沒有先命中券不足、已出貨或指定日時，才進入未出貨稽核
狀態為 MatchWithoutQuota、Unmatch、Cancel 或 Reward 時會跳過 BookingTime 稽核。給點與給券的判斷順序略有不同，尤其給券會先檢查券不足。

未出貨時，預期時間從哪裡算？

比對門檻也有版本差異：2025 年案例所對應的舊版要求時間差小於 1 小時；現行程式在 RewardDays > 0 時使用 Math.Max(bucketCount, 3) 小時，且採用「小於或等於」。現行三桶設定下就是最多 3 小時。

午夜像一道看不見的換日線。訂單在 23:54 成立，紀錄在 00:02 更新，鐘面只差八分鐘；一旦先取日期再加 N 天，兩邊就可能像拿到不同日期的車票，整整差一天。修正程式碼記錄的問題，正是正流程與舊稽核用了不同的起算時間。

八分鐘如何變成一天

原案留下哪些時間證據？

DDB 欄位 原始 UTC 值 換算為 UTC+8
OrderTimeUTC 2025-11-05 15:54:52Z 11/05 23:54:52
UpdateTimeUTC 2025-11-05 16:02:14Z 11/06 00:02:14
BookingTimeUTC 2025-11-12 16:00:00Z 11/13 00:00:00
工作項目 VSTS 546845 記錄了「時間差異 24.00 小時」的稽核警報，但沒有提供 RewardDays。因此可以確認訂單成立與更新跨過 UTC+8 的午夜，也能確認稽核曾報出 24 小時差異；僅憑這三個 UTC 欄位，無法完整重算該筆 BookingTimeUTC。若把它當成「+7 天」並算成 2025-11-12 00:00Z，會與實際儲存的 16:00Z 不符。

修正提交 0dadda61 的程式註解與分支指出：未延遲的線上加 N 天回饋，正流程以 OrderTime 起算；舊稽核卻可能以 UpdateTime 起算。兩者跨過本地午夜時，稽核就可能用隔天的答案卡比對原本的排程。

稽核要分辨「剛建立的預約」和「後來真的改過期的預約」，不能只看 UpdateTime 比訂單時間晚。它會翻回饋歷史，尋找一個特定的改期記號。就像行事曆有沒有留下「已改期」標籤，決定接下來該拿哪一天對答案。

改期記號怎麼找？

沒有找到關鍵字，只表示歷史資料沒有記錄到這個改期記號，不能推論世界上從未發生過其他更新。這個判斷是稽核選擇時間基準的程式規則，不是對所有更新原因的完整分類。

規則看起來像一團耳機線，攤開成「情境、時間基準、比對方式」就比較好解。先找出稽核走哪條路，再問它拿哪個時間當答案；跳過狀態、券不足與指定日期，都有自己的優先順序。

各情境拿哪份答案卡？

情境預期時間的來源稽核如何比
MatchWithoutQuota、Unmatch、Cancel、Reward不計算直接略過
線上未出貨、加 N 天、沒有改期記號OrderTime + RewardDays案例當時取日期；現行再套用分桶，與 BookingTime 比
線上未出貨、加 N 天、有改期記號UpdateTime + RewardDays案例當時取日期；現行再套用分桶，與 BookingTime 比
線下未出貨OrderTime + RewardDays加 N 天時取日期並比對 BookingTime
未出貨、RewardDays = 0線上以 UpdateTime；線下以 OrderTime保留時分秒，比對 BookingTime
指定日期回饋活動設定的 RewardDateTime與 BookingTime 精確比對
已出貨回饋最後出貨時間加回饋天數，且不早於活動有效日比對 BookingDate 的日期
券不足重試依 UpdateTime 排到當天 22:00、當天或隔天 10:00與 BookingTime 精確比對
這張表是查閱地圖，不等於所有分支可以任意交換順序。給點遇到「已出貨且指定日期」會走指定日期稽核；給券則先看券不足，再看已出貨。未出貨分支才是本文跨日問題的主角。

比對門檻別拿錯版本

案例當時的未出貨路徑

預期與實際差異須小於 1 小時；等於 1 小時也會失敗。

現行未出貨加 N 天

使用分桶後的預期值，容忍時數為 Math.Max(bucketCount, 3)，邊界採小於或等於。

指定日期與券不足

比較設定的精確時間，不套用上述未出貨加 N 天的容忍值。

把案件放回時間線，就能看清楚當時的警報與後來的程式修正。訂單成立和紀錄更新只隔了幾分鐘，卻分處午夜兩側；當稽核拿更新時間重新算日期，就可能拿到隔天的答案。

發生環境

原始工作項目記錄為 HK-Prod，時間換算採 UTC+8。

觀察到的警報

BookingTime 與預期不符，回報時間差異 24.00 小時。

程式修正

未延遲的線上加 N 天回饋，稽核改用 OrderTime 起算。

案件與程式變更的時間線

已能確定的修正方向是：初始且未留下延遲記號的線上加 N 天回饋，稽核應與正流程使用相同的 OrderTime 日期基準。現行稽核程式仍保留這個分支，並與三桶分配共用計算元件。
原始資料還缺哪些欄位，才能完整復算？
  1. 該筆回饋實際設定的 RewardDays，以及適用的回饋條件。
  2. 應用程式讀入三個 UTC 欄位時的 DateTime 時區轉換與日期基準。
  3. 修正版本在 HK-Prod 的實際上線時間與上線後的稽核結果。

在這些資料補齊之前，本文只把「24 小時警報」與「修正程式選擇的時間基準」當作已確認事實，不把示意用的加 7 天算式冒充該筆訂單的實測結果。
