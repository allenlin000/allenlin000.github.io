Bookingtime Job 本身的記憶體累積問題

Created2026-10-21|Updated2026-10-25|PromotionReward
|Post Views:

表面上，NMQ 只派來一個 Dispatcher Job。它拿著 ExecuteTime 去 DDB 查資料，卻可能撞上一整車同時到站的點數與優惠券回饋。GetRemainingAsync() 更有「我全都要」的氣勢：這個時段符合查詢條件的紀錄，不管分成幾頁，都先讀進來。

接下來還得過濾、分組、上傳 S3、組裝 NMQ 請求。舊資料還在手上，新清單又排隊上車。車越擠，Pod 記憶體越吃緊；嚴重時可能 OOM Killed，同一個 Worker 的其他 Job 也會受影響。

一個 Job 怎麼扛成這樣？ 接下來從它怎麼查、怎麼分、怎麼派，一步步拆開看。

16:01:10 UTC，Dispatcher 打卡上班。NMQ 給它一份含 ExecuteTime 的 task data，卻沒有附上待回饋名單。Job 先驗證、解析這份資料；上一個時段該發給誰，還得自己去 DDB 找。

16:01 上班，為什麼回頭查 15:00？

這次用 ExecuteTime = 2026-09-17T16:01:10Z 模擬。程式先往前一小時，再截到整點，得到 startTime = 15:00:00 UTC；原時間截到整點，得到 endTime = 16:00:00 UTC。因此，這次找的是 2026 年 9 月 17 日 15:00 到 16:00 的紀錄。

實際公式是 startTime = ExecuteTime.AddHours(-1).ToHour()、endTime = ExecuteTime.ToHour()。DDB 使用 BookingDateUTC-BookingTimeUTC-index，條件為 BookingDateUTC = 2026-09-17 且 BookingTimeUTC Between 15:00:00Z and 16:00:00Z。

DDB 找到五筆，但不是五筆都要發

下面七筆都是示意資料。時間均為同一天的 UTC；A、B、C 代表不同的 (ShopId, MemberId, PromotionEngineId) 群組。

紀錄BookingTimeUTCRewardStatus群組／類型OrderTime
R014:59:59WaitToRewardA／給點14:10
R115:03:00WaitToRewardA／給點14:50
R215:20:00WaitToRewardA／給點14:30
R315:45:00WaitToRewardB／給券15:10
R415:48:00非 WaitToRewardC／給點15:15
R515:59:00WaitToRewardC／給點15:30
R616:00:01WaitToRewardC／給點15:40

R0 早了一秒，R6 晚了一秒，都不在查詢區間內。DDB 回傳 R1 到 R5；GetRemainingAsync() 會讀完所有頁面，所以這五筆先一起進入本次 Job。此時 R4 也在其中，因為 RewardStatus 是稍後才由程式端 FindAll 過濾。另須留意：Between 包含兩端，若有紀錄剛好落在 16:00:00，也會被這次查到。

五筆資料，最後怎麼變成三個任務？

A、B、C 的分組鍵分別是 (1001, 2001, 3001)、(1001, 2002, 3002)、(1002, 2003, 3003)。A 組雖然先查到 R1、再查到 R2，但 OrderTime 較早的是 R2，所以會員訂單清單會排成 R2 → R1。每組各上傳一份 S3 資料，先累積三個 CreateTaskRequest，之後才逐筆建立 NMQ 任務，並累積 CreateTaskResponse 與 TaskId 清單。A、C 走給點路由，B 因為是 ECoupon 走給券路由。

五筆變四筆，四筆再變三個任務，記憶體卻不一定跟著「減肥」。原始查詢結果、過濾與分組結構，以及後續請求與回應，可能在同一輪處理中重疊。這些是程式流程可見的累積來源；實際記憶體峰值與 OOM 是否由此造成，仍須量測確認。

上一段的資料從五筆縮成四筆，最後變成三個任務。數字一路變小，Job 手上的東西卻不一定跟著變少：查回來的紀錄還在，新的清單、分組與派送資料又陸續加入。

記憶體是在哪些地方被占住的？

查詢：整箱先搬進來

GetRemainingAsync() 讀完這個時段的所有頁面，整批 records 留在同一次 Job 裡。既有的查詢 logging decorator，在一定筆數內還會序列化完整結果。

規劃改善每次只讀一頁；新查詢方法只記必要摘要。

加工：邊整理邊多拿幾份

FindAll 建立待回饋清單，GroupBy 建立分組結構，兩者會持有 record 的參考。每組轉成會員訂單資料並上傳 S3 時，還可能產生 DTO、字串與序列化 buffer。

規劃改善只在頁內過濾與分組；每組處理完就不再保留轉換與上傳的暫存資料。

派送：清單還在排隊

目前先累積整輪的 taskRequests，再逐筆建立 NMQ 任務；responses 與 TaskIds 清單也跟著增加。

規劃改善每組完成後直接建立 NMQ 任務，只保留成功數量的統計。

這三組是程式碼可確認的配置來源，卡片大小不代表實際記憶體占比。它們也不表示 OOM 已找到唯一根因；改善幅度仍須用 profiler 與壓測量測。逐頁處理可能改變跨頁分組與排序，後面的方案段落會接著討論這個代價。

把整車資料搬進記憶體後才說「只拿一千筆」，有點像貨都卸完了才開始限重。這次真正要動的，是查詢入口：一次只讀一頁，處理完再沿著續頁位置往下走。

先看選擇路徑

本文件先選「同一個 Dispatcher 帶 token 逐頁派送」作為主方案。它能限制單次查詢持有的資料量，也不用為每一頁再建立一個 Dispatcher Job，或新增 DDB 的派送狀態。不過，整輪執行時間仍可能很長；同一會員、同一活動的紀錄若跨頁，原本合成一個任務並依 OrderTime 排序的行為也可能改變，重試時的重複派送問題仍在。

主方案是本文件的設計方向，還不是可直接啟用的結論。若業務必須保留跨頁的完整分組與順序，應改評估外部暫存後再完整分組；不能把跨頁紀錄一路留在 RAM，否則又回到原本的記憶體問題。

「先查一千筆，滿了就再叫下一個 Dispatcher」聽起來像接力賽。問題是下一棒沒有拿到接力棒，只拿到同一張起點地圖。每個 Job 都從相同時段的開頭查，後面的紀錄可能一直等不到人。

第二棒為什麼還在起點？

即使前段紀錄已完成回饋，只要 BookingTime 仍符合索引條件，它們仍可能占住這次 Query 評估的名額；RewardStatus 是回到程式後才過濾。只看「本次拿到幾筆」也不可靠：DynamoDB Query 可能先碰到 1 MB 上限，還沒滿 1000 筆就已停在頁面邊界。AWS Query 官方文件

要知道下一頁從哪裡開始，應使用查詢回傳的續頁位置。筆數是否滿 1000，既不能代替 token，也不能證明後面的資料已經讀完。

替 DDB 紀錄貼一張「已派送」標籤，乍看能讓下一輪跳過它。但貼標籤和建立 NMQ 任務分屬兩個系統；中間只要斷在不同位置，結果就不同。

先做哪件事，都有一個空檔

執行順序中斷時可能留下什麼
先寫 Dispatched，再建立 NMQ 任務NMQ 建立失敗，紀錄卻已標記為派送，可能漏發。
先建立 NMQ 任務，再寫 DispatchedDDB 更新失敗，下次可能把同一批再派一次。
先查未派送，再由各 Dispatcher 更新兩個 Dispatcher 可能同時看到同一筆，需要 conditional update 搶佔。

還有補發情境：券不足時會更新 BookingTime，單一布林標記無法區分「上一次已派」和「這一次應重派」。若要把 Dispatched 做成可靠的業務狀態，還得設計版本識別、租約到期、搶佔與恢復流程。

這條路線處理的是跨系統派送狀態，不只是減少單次 Job 的記憶體。它值得另開設計，本次先不把它塞進分頁改善。

token 比較像夾在書裡的書籤：它告訴查詢下一次從哪裡接著翻，沒有替任何一頁蓋上「回饋完成」的章。把這兩件事混在一起，分頁就會看起來很順，重試時卻可能出事。

一頁的「筆數」和「下一頁」是兩回事

DynamoDB 單次 Query 最多先讀到 1 MB，或先達到指定 Limit，然後才套用 FilterExpression。因此 Limit = 1000 控制的是評估筆數，不保證回傳 1000 筆；本頁甚至可能沒有符合資料，卻仍帶有續頁位置。AWS Query 官方文件

名稱讀這個值時要知道的事
Items本頁回傳資料，之後還可能由程式過濾 WaitToReward。
CountDDB 回傳筆數；若使用 FilterExpression，是過濾後的筆數。
ScannedCount本次評估筆數，位於 DDB 過濾之前。
LastEvaluatedKey低階 Query 回傳的完整續頁 key。
ExclusiveStartKey低階 Query 下一次請求的起始位置。
NextToken本專案擬定的分頁合約名稱；型別與 SDK 對應仍待確認。

低階 API 會將這次回傳的 LastEvaluatedKey 原樣交給下次請求的 ExclusiveStartKey。它不是單純的最後一筆 BookingTime，也不是天然的字串 token；若要使用 SDK 高階 PaginationToken，得先確認目前套件與查詢 API 的支援方式，兩種表示不能直接混用。AWS 分頁說明

書籤要完整

原樣保存 SDK token 或完整 key，不能只留 BookingTime；同一時間有多筆資料時，簡化後可能跳過紀錄。

翻頁條件要固定

同一輪的 table、index、時間範圍、排序及查詢條件保持一致。有續頁 key 就繼續，即使下一頁沒有有效回饋資料。

書籤不管派送

token 不提供 NMQ 去重，也不證明資料已回饋。多次 Query 不是固定快照；執行中新增或移動排序位置的紀錄，不能保證本輪全讀到。

若部署中的索引實際是 GSI，只能採最終一致性讀取。新查詢實作須核對索引與 SDK 設定，不能照抄既有 ConsistentRead = true 就認定可用。AWS Query 官方文件

要替 Dispatcher 換成逐頁處理，先得留好回頭的路。入口仍收原本的 ExecuteTime，開關沒開或設定讀不懂，就走舊流程；開了才進新流程。兩條路從入口分開，避免新程式不小心改變舊方法的意思。

開關在入口決定，這一輪不換車道

以下名稱是規劃值，實作時可依專案慣例調整。

設定預設值這次 Job 會怎麼做
_N1CONFIG:BookingDispatcherPaginationEnabledfalse只有 true 走新分頁流程；缺少或無法解析時走舊流程。
_N1CONFIG:BookingDispatcherPageSize1000新流程單次查詢上限；缺少、無法解析或非正值時回退到 1000。

單次 Job 開始時就讀取模式與 page size，整輪固定使用，不在處理到一半時切換。正整數上限是否另設邊界，留待設定驗證時決定。

逐頁處理需要一張說清楚的交接單：這一頁拿到什麼，下一頁從哪裡接。少了後半句，Job 只是在縮小眼前的資料，沒辦法安全地往後翻。

單頁結果要交代的三件事

建議新增暫名 QueryPageEntity<T>，維持一類別一檔案。

欄位合約
Items當頁集合；沒有結果時回空集合，不回 null。
NextToken沒有下一頁時回空值；具體型別等 SDK spike 後定案。
EvaluatedCount，選用SDK 若能提供，就記錄評估筆數；不能拿 Items.Count 冒充。
續頁位置必須接在「已完整處理的本頁」後面。如果先讀一大頁、自己 Take 一部分，卻使用整頁尾端的 token，剩下尚未處理的紀錄會被直接跳過。

這一版的節奏是「先寄完這一頁，再翻下一頁」。提早抓後頁，或上一頁任務還沒建好就先移動 token，看似跑得快，出錯時卻很難回答究竟漏了哪一批。

一頁處理完，才輪到下一頁

Job 先解析輸入與設定，固定 startTime、endTime 和 page size。接著只讀一頁，檢查本頁 Items 與候選 NextToken；不預先並行抓取後續頁面。

有待回饋紀錄時，頁內仍按 (ShopId, MemberId, PromotionEngineId) 分組，組內依 OrderTime 排序。每組建立會員資料並上傳 S3，確認上傳成功才建立對應 reward Job；S3 key 格式、member request 結構與 GetJobName 路由沿用現行規則。整頁所有組都派送成功，才前進到下一頁。

頁內處理放進短生命週期方法，不把頁內物件塞進跨頁集合；全輪只留頁數、筆數、成功任務數與耗時等摘要。GC 何時回收由 runtime 決定，這裡不靠每頁 GC.Collect，也不保證 process working set 會每頁立即下降。

SDK 回傳無效或不前進的 token記錄可診斷摘要並失敗，避免靜默重頭查或無限迴圈。

記憶體省下來了，卻可能把同一位會員的訂單拆成好幾份。DDB 是按 BookingTimeUTC 翻頁，不會因為兩筆屬於同一個會員，就好心把它們放在同一頁。

同一組 30 筆，可能變三個 Job

假設同一 (ShopId, MemberId, PromotionEngineId) 在查詢時段有 30 筆訂單，分別落在第 1、2、3 頁。舊流程先把所有頁讀完，組成一個 Job，30 筆依 OrderTime 排序。新流程每頁處理完就派送，會變成三個 Job，每個只排自己手上的訂單。

Dispatcher 即使先建立 Job 1，再建立 Job 2，也不能推論 reward Worker 會照這個順序完成。拆組還會增加 S3 物件、NMQ 任務和 lock 競爭；lock 能限制同時處理，不代表先來先做。

這是啟用開關前的門檻：若同會員、同活動必須先處理較早訂單，新流程不能直接啟用。先查核順序是否影響累積門檻、活動額度及給券／給點結果，再決定是否需要跨頁合組。

若業務不能接受拆組，需改用外部暫存後完整分組，或設計其他能保留順序的處理方式。把跨頁會員資料一直留在 RAM，會讓這次的記憶體改善繞回原點。

續頁 token 可以告訴 Job 下一頁在哪裡，卻不知道上一頁的 NMQ 任務有沒有真的建好。Job 跑到一半斷線時，故事不會自動從「上次看到這裡」接演。

本輪的進度，只存在本輪記憶體裡

本方案不新增業務紀錄狀態，也不持久化 token。查到本頁後，先把本頁需要的任務派完；成功才翻頁。任何一步失敗，都讓本輪失敗，不吞掉例外，也不臨時改走全量流程。

中斷在哪裡，後果就不一樣

失敗或變動可能留下的結果本次處理與待確認處
Query 失敗當頁未派送。讓 Job 失敗，保留錯誤供排查。
S3 失敗該組尚未建立 NMQ；前面幾組可能已成功。停止本輪；重試可能重複派送前組。
S3 成功、NMQ 失敗可能留下沒有任務使用的 S3 物件。不記成成功；確認現有 S3 清理生命週期。
NMQ 成功、回應遺失Dispatcher 不知道任務其實已建立。重試可能再建立一次；token 無法去重。
後頁失敗或程序中斷先前頁的任務已建立，後頁尚未完成。初版不持久化 token；宿主若重試，從原時段第一頁重跑。
另一個 Dispatcher 同時查同一時段兩輪可能派送同一筆紀錄。token 是查詢位置，無法當跨執行鎖。
執行中新增或改動 BookingTime紀錄可能移入已讀區段。不能保證本輪全讀到；確認既有補掃。
索引更新延遲本輪可能暫時看不到新資料。若是 GSI，需接受最終一致性並確認補掃。
上線前要查明：下游的 lock、最新 RewardStatus 檢查，以及外部給券／給點是否具備冪等性。即使有 lock，也不能直接推論重跑不會重複產生業務效果。

本次不直接新增補掃 Job。實作前要確認現有 audit、redo 或補掃機制是否能接住漏讀與中斷；若沒有，補償方案就是上線前必須決定的事，不能說「有 next token 就保證不漏發」。

想自己對照時間區間，可以從這份 task data 開始。它的時間帶是 +08:00，換成 UTC 後是當天 08:01:10.6854808Z；依前面的公式，查詢區間會落在 07:00:00Z 到 08:00:00Z。

這筆資料和前面用 16:01:10Z 解說的示意案例不是同一個執行時間。要比對 DDB 查詢結果，請以實際輸入的時區換算後，再看 BookingDateUTC 與 BookingTimeUTC。
