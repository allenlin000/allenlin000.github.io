佔額

Created2026-10-27|Updated2026-10-27|PromotionReward
|Post Views:

「佔額」是回饋活動在 PromoCodePool Service（PCPS） 的 Group 中，先替符合條件的訂單會員分派並兌換一筆 Code，使該筆回饋占用活動限額。這是配額操作，不是給點或給券。Promotion Worker 另外在 DynamoDB（下稱 DDB）存回饋主單及子單狀態，藉此決定後續是否能回饋、取消及稽核

本專案支援三種相關活動類型：RewardReachPriceWithPoint2、RewardReachPriceWithRatePoint2、RewardReachPriceWithCoupon。有 GroupCode 才屬於佔額活動；分派器使用 IsNullOrWhiteSpace 過濾，Job 的 IsQuotaPromotion 使用 IsNullOrEmpty 判斷，兩處對純空白字串的結果不同，屬於值得留意的邊界。[S1][S4]

flowchart LR
  E1[EDA OrderPlaced] --> D[PromotionRewardOccupyDispatcherJob]
  D --> P[點數 V2 Job]
  D --> C[給券 Job]
  P --> X[規則與訂單試算]
  C --> X
  X -->|IsMatch| PCPS[PCPS dispatch-and-redeem]
  PCPS --> DDB[DDB 回饋紀錄]
  E2[EDA OrderCreated] --> R[OrderCreated 分派器]
  R -->|限額活動延後 5 分 10 秒| P
  R -->|限額活動延後 5 分 10 秒| C
  DDB --> P
  DDB --> C
  P --> OUT[BookingTime 到期後給點]
  C --> OUT2[BookingTime 到期後給券]
  E3[EDA OrderFailed] --> D
  D -->|僅 Occupy| REV[PCPS reverse-redeemed-and-dispatched]
  REV --> CAN[DDB Cancel]
概念／服務 職責 關鍵資料
Promotion Service / Engine 查訂單時間有效的活動與活動規則；試算是否符合活動 PromotionEngineId、活動類型、GroupCode、IsMatch
NMQv3 分派每個活動的點數／券 Job；同一 Job 依 EventSource 走佔額或回饋 OrderPlaced、OrderCreated、OrderFailed
PCPS 真正分派、兌換、查詢與返還配額 Code GroupId/GroupCode、CodeId、ReceiverId、Labels、State
DDB 與 Locker 保存回饋主／子單及歷程；以訂單＋活動鍵鎖住並行處理 Occupy、WaitToReward、MatchWithoutQuota、Cancel
點數中心／券服務 在回饋條件與 BookingTime 成立時實際發點／發券 Reward、明細、已給／回收數量
稽核器 對照 DDB 回饋狀態和 PCPS 實際佔額筆數 期望 0 或 1 筆

PCPS 請求的 ReceiverId 是會員 ID 字串，Tags 為空集合，Labels 放訂單彙總碼 TG；後續以 GroupCode + TG 查佔額。HTTP 標頭帶 ny-market、ny-shop-id、ny-source-type=PromotionReward、ny-user-id。線下訂單查 DDB／PCPS 時使用 CrmSalesOrderCodePrefix + CrmSalesOrderId 作為代碼。[S2][S5]

Rule-Record 會存 GroupCode

建立與更新

活動時間與佔額群組時間

回饋活動的有效期和 PCPS 佔額群組的有效期是兩組設定。活動規則的 Since、Until 分別採用活動的 StartDateTime、EndDateTime，用來判斷訂單在下單當時是否符合活動時間。建立 PCPS 群組時，Since 同樣採用活動開始時間，但 Until 固定為 DateTime.MaxValue，沒有跟著活動結束時間到期。因此，活動已結束後，只要補跑流程仍能找到該活動與訂單，過去符合活動期間的訂單仍有機會在現在向 PCPS 佔額。[B1][B2][B3]

情境 活動時間判斷 PCPS 群組時間判斷 結果
現在補跑活動期間內的舊訂單 訂單時間落在活動開始與結束之間 群組的 Until 尚未到期 時間設定不會阻止佔額，仍須符合活動條件且有額度
現在處理活動開始前的訂單 訂單時間早於活動開始 即使群組已存在 訂單不符合活動時間，不應進入該活動佔額
現在提前處理未來活動的訂單 訂單時間可能落在未來活動期間 處理當下早於群組 Since 依群組設定不應提前佔額；PCPS 的實際拒絕行為仍須以 PCPS 實作確認

建立活動時，backend API 只對支援佔額的回饋類型且 Quota > 0 的活動建立並啟用 PCPS 群組，取得 GroupId 後寫入 PromotionEngine_GroupCode。Quota = 0 代表不建立佔額群組。活動開始後，更新流程會直接跳過佔額設定變更。[B4][B5]

這個時間設定解決的是 PCPS 群組過期問題，不保證任意久以前的活動都能由一般 Worker 分派器找出。目前該分派器的候選活動查詢從現在往前七天開始，再用訂單時間過濾；超過查詢範圍的補跑仍需檢查實際入口。[B6]

資料表

PromotionEngine_GroupCode

線上訂單（ECom）

  1. OrderPlaced 到達佔額分派器。它按訂單時間選出有效的三類回饋活動，保留有 GroupCode 的活動；點數活動還需 ExtendInfo 有值。每檔活動各建一個點數 V2 或券 Job，要求的 EventSource=OrderPlaced。分派本身尚未扣額度。[S1][S6]
  2. Job 取得同一筆 PromotionRuleRecord，做通路檢查和回饋試算。在 DDB key 上取鎖；沒有既有紀錄、IsMatch=true 才向 PCPS 呼叫 dispatch-and-redeem。回傳 State=Redeemed 才當作成功；配額不足則記為失敗。之後寫入 DDB 主／子單。既有紀錄則直接返回，以 DDB 作為重跑的防護之一。[S2][S3][S7]
  3. OrderCreated 進入另一個分派器。對有 GroupCode 的活動，它把回饋 Job 的 BookingTime 設成 UtcNow + 5 分 10 秒，試圖讓佔額流程先完成。回饋 Job 若查不到線上佔額活動的 DDB 紀錄，會拋錯而不直接給點／券；查到 Occupy 才建立績效 Job 並轉 WaitToReward。到真正回饋時間前不執行給點／券。[S8][S3][S7]

線下訂單（Others）

線下回饋 Job 若尚無 DDB 紀錄，會直接試算；符合活動且有 GroupCode 時在同一次回饋流程呼叫 PCPS 佔額，再插入 DDB。成功的線下紀錄初始即為 WaitToReward，不會經過線上訂單專用的 Occupy 暫存狀態。OrderFailed 返還會略過規則通路完全不含 Web／iOS／Android 的純線下活動。[S3][S7][S9]

條件 PCPS 動作 DDB 主單結果 後續
沒有 GroupCode 無 中活動為 WaitToReward，未中為 Unmatch 一般回饋路徑
有 GroupCode，試算未中 無 Unmatch 不給點／券
有 GroupCode，試算中，PCPS 回 Redeemed，線上 OrderPlaced 分派並兌換 1 Code Occupy 等 OrderCreated 轉狀態
有 GroupCode，試算中，PCPS 回 Redeemed，線下 分派並兌換 1 Code WaitToReward 按 BookingTime 回饋
有 GroupCode，試算中，額度不足或回傳狀態非 Redeemed 佔額未確認成功 MatchWithoutQuota 不進入回饋
線上回饋 Job 無 DDB 紀錄 無 不建立 拋錯，待前段佔額資料釐清
線上回饋 Job 讀到 Occupy 無新佔額 Occupy → WaitToReward 建績效 Job，後續給點／券
OrderFailed 且 DDB 為 Occupy 查 Code 並返還 Occupy → Cancel 券另增加取消數量 
stateDiagram-v2
  [*] --> Unmatch: 試算未中
  [*] --> MatchWithoutQuota: 中活動但 PCPS 未成功
  [*] --> Occupy: 線上 OrderPlaced 佔額成功
  [*] --> WaitToReward: 線下佔額成功／非佔額活動中獎
  Occupy --> WaitToReward: OrderCreated 回饋 Job
  Occupy --> Cancel: OrderFailed 返還 PCPS 成功
  WaitToReward --> Reward: 達 BookingTime 且回饋成功
  WaitToReward --> Cancel: 取消／逆流程重算後不符條件
  Reward --> Cancel: 全部回收或相關取消流程

Reward 等狀態的後續逆流程有多種分支；上圖呈現與佔額直接相關的主要轉換，不代表每種回收情境都必定直接寫 Cancel。點數與券插入紀錄的狀態判斷一致。[S10]

操作 Worker 呼叫 重要語意
佔額 POST api/groups/{groupId}/dispatch-and-redeem 成功 HTTP 回應仍需 State=Redeemed 才算佔額成功。[S5]
查 TG 佔額 GET api/codes/get-by-label?GroupId=...&Label=...&Limit=30 Labels 是查詢註記；GetMemberPromotionQuotaInfoByTradesOrderGroup 要求恰好一筆。[S5]
返還 POST api/codes/{codeId}/reverse-redeemed-and-dispatched 以 GroupId、ReceiverId 返還；OrderFailed 使用單筆返還，逆流程 helper 可逐筆返還。[S5][S11]
失敗／例外 程式處理 影響
佔額 HTTP 409 轉 InsufficientQuotaException，不重試 Job 回 isOccupy=false，符合活動者記 MatchWithoutQuota。[S5][S2]
佔額網路／其他 HTTP 錯誤 Client 有有限次重試；仍失敗拋例外 Job 包為可釋放鎖的失敗；不應解讀成「額度不足」。[S5][S2]
佔額成功但寫 DDB 失敗 PCPS 與 DDB 分開呼叫 可能留下 PCPS 已兌換、DDB 缺漏；這是由呼叫順序推得的一致性風險，需靠查 PCPS 與任務日誌確認個案。[S2][S10]
OrderFailed 找不到 DDB／PCPS Code DDB 查詢有限次重試；單筆查不到或非恰好一筆會拋錯 不會默默把 DDB 寫 Cancel。[S1][S11]
逆流程 ReverseOccupyQuotaAsync 查無／未兌換 容忍並結束；Timeout／TaskCanceled 最多三次 這與 OrderFailed 的嚴格單筆返還路徑不同。[S11]

注意：PromotionRewardOccupyDispatcherJob 有 OrderFailedDelaySeconds=30 常數與「增加等待時間」註解，但目前 ProcessQuotaReverseRedeemed 呼叫前**沒有使用該常數或 Task.Delay**。該路徑以 DDB 讀取／鎖的重試應對先後順序，不宜宣稱實際固定等待 30 秒。[S1]

OrderFailed 走佔額分派器的另一分支：以訂單時間再找有 GroupCode 的活動，排除純線下活動，依活動類型取得點數／券 DDB 紀錄。只有 RewardStatus=Occupy 才返還；Unmatch、MatchWithoutQuota、Cancel 略過，其餘狀態當異常。返還先從 PCPS 以 TG 查到單筆 Code，再呼叫 Reverse；成功後把主／子單改 Cancel，券另外更新道具表 CanceledCouponQty。[S1][S9][S11]

訂單後續取消、退款或重算也可能返還已佔額資源。點數流程在重算後不符合活動時呼叫 ReverseOccupyQuotaAsync；券流程在整單取消，或重算應給券 0 且尚未給券時呼叫它。該 helper 以 TG 查可能多筆 Code，逐筆 Reverse，查無／未兌換視為可容忍，逾時有限次重試。返還時機不限付款失敗。[S12][S13][S11]

PromotionRewardQuotaAuditor 對有 GroupCode 的活動用 CheckOrderOccupiedQuota 查 PCPS：Occupy／WaitToReward 預期恰一筆，未完全回收的 Reward 也預期恰一筆；Unmatch／Cancel／MatchWithoutQuota 預期零筆。點數已全回收的 Reward 預期零筆。這是辨別 DDB 與 PCPS 是否一致的最直接規則。[S14]

排查一筆訂單時，先固定 ShopId + PromotionEngineId + TG + MemberId，再核對：① 活動類型、有效時間、GroupCode、規則通路；② OrderPlaced／OrderCreated／OrderFailed 的 Job 與時間；③ DDB 主單狀態及歷程；④ PCPS 依 GroupCode＋TG 查到的 Code 數、State、CodeId；⑤ 逆流程是否已執行。不要只看 IsMatch 就判定有額度，也不要只看 DDB Occupy 就略過 PCPS 實際狀態。[S1][S14]
